> 目标：把「看懂用户、管住钱、顺畅收款」这三件事做成产品自带的后台，而不是停在文档里。

## 二、客户信息

### 2.1 客户列表

`GET /api/admin/customers`

| 参数 | 说明 |
| --- | --- |
| `keyword` | 用户名 / 昵称 / 邮箱 / 手机号模糊匹配 |
| `status` | `active` / `disabled` |
| `level` | `normal` / `vip` / `svip` / `agent` |
| `deptId` | 部门过滤 |
| `from` / `to` | 注册时间范围，`YYYY-MM-DD` |
| `page` / `pageSize` | 默认 1 / 20，pageSize 上限 200 |

返回每行的账务汇总：`balance`（当前算力）、`totalPaid`（累计实付，元）、`totalSpent`（累计消耗）、`refundAmount`（累计退款）、`orderCount` / `paidOrderCount`、`lastPaidAt`。

> 说明：汇总按订单与流水实时计算，已退款订单会从 `totalPaid` / `paidOrderCount` 中扣除，但保留 `lastPaidAt`（退款不代表没付过）。

### 2.2 客户详情与档案

- `GET /api/admin/customers/meta`：等级、来源、状态等枚举（前端下拉框直接用它，避免硬编码）。
- `GET /api/admin/customers/:id`：基础资料 + 最近订单 + 最近流水 + 档案字段。
- `PUT /api/admin/customers/:id`：`level` / `source` / `tags` / `remark` / `nickname` 等运营字段。档案落在 `customer-profiles.json`（0600 权限），不污染账号库。

### 2.3 人工调账

`POST /api/admin/customers/:id/adjust` `{ amount, reason }`

- `amount` 为整数、可正可负；负向调账后余额不得为负（否则 400 中文报错）。
- 调账会写一条 `type:"grant"` 流水，`reason` 前缀「人工调账：」，并落审计 `admin.action`。
- 所有账务都走 `credits.adjust()`，与充值/消费共用同一本账，保证「余额 == 流水求和」不变式。

### 2.4 数据范围

沿用账号体系的行级数据范围：`all` / `dept` / `self` / `custom`。超级管理员直通；越权访问详情返回 `403 FORBIDDEN`，目标不存在返回 400（不泄露存在性）。

## 三、充值后台

### 3.1 订单与统计

- `GET /api/admin/recharge/orders`：`status`、`channel`、`userId`、`keyword`、`from` / `to`、分页；响应含 `summary`（当前筛选下的笔数/金额）。
- `GET /api/admin/recharge/stats?days=7`：今日收入、区间收入、退款额、按通道/状态分布、按天趋势（自然日补零）、Top 客户。

### 3.2 运营动作

| 动作 | 路由 | 说明 |
| --- | --- | --- |
| 人工补单 | `POST /orders/:id/manual-paid` | 仅 `pending` 可补；已支付返回 `{ok:true,already:true}`（幂等）；已退款/已取消返回 400 |
| 主动查单 | `POST /orders/:id/sync` | 调聚合平台 `queryOrder`；金额（分）与订单不符、查单失败都拒绝入账 |
| 退款 | `POST /orders/:id/refund` | 仅 `paid` 且未退；先校验余额足够扣回「套餐算力 + 赠送算力」，再写 `type:"refund"` 负流水 |
| 备注 | `POST /orders/:id/note` | 只追加备注，不动账 |
| 套餐改价 | `GET/PUT /api/admin/recharge/plans` | 改价落 `recharge-plans.json`，立即对新建订单生效；内置套餐作为兜底 |

> 退款不会自动调微信/支付宝退款接口（那需要商户证书与人工复核），这里做的是**账面冲正 + 算力扣回**；真实资金退款仍在支付平台后台操作，完成后回到本后台点「退款」平账。

## 四、自动管理充值

配置：`GET/PUT /api/admin/recharge/automation`

| 配置 | 默认 | 范围 | 作用 |
| --- | --- | --- | --- |
| `enabled` | `true` | 布尔 | 总开关 |
| `expireMinutes` | 120 | 5 ~ 1440 | 待支付订单超过该分钟数自动关闭 |
| `syncAfterSec` | 180 | 30 ~ 3600 | 下单超过该秒数后，向聚合平台查单补到账 |
| `syncBatch` | 20 | 1 ~ 100 | 单轮最多查多少笔 |

- 服务端启动后每 60 秒跑一轮（`setInterval().unref()`，不会拖住进程退出）；`AI_CANVAS_DISABLE_AUTOMATION=1` 可整体关闭。
- `POST /api/admin/recharge/automation/run` 可手动跑一轮，返回 `{at, expired, synced, paid, errors}`，并持久化 `lastReport` 供页面回看。
- 自动查单候选口径：`pending` 且「通道为空或 aggregator」——微信/支付宝直连订单由各自回调负责，不去轮询。

## 五、接入第三方聚合平台

### 5.1 支持的协议

| provider | 适配平台 | 下单 | 回调 |
| --- | --- | --- | --- |
| `epay` | 易支付 / 蓝兔等兼容协议 | GET `submit.php`，取 302 收银台地址 | GET/POST 表单 |
| `xunhupay` | 虎皮椒 | POST 创建订单，返回 `payUrl` / 二维码 | POST 表单，成功态 OD/CD |
| `custom` | 自建聚合网关 | POST JSON + `X-Agg-Sign`（HMAC-SHA256(rawBody, key)） | JSON，支持 rawBody 验签 |

支付方式统一为 `wxpay`（微信）/ `alipay`（支付宝），前端选「微信/支付宝」后由服务端映射。

### 5.2 配置步骤

1. 运营后台 → 支付通道 → 选「聚合支付」→ 选协议商（易支付 / 虎皮椒 / 自建）。
2. 填 `gateway`（如 `https://pay.example.com`）、`pid`、`key`（自建还需要 `appid` / `appsecret`）。
3. `notifyBaseUrl` 填**公网可达**的站点根地址（如 `https://ai.example.com`），回调地址自动拼成：
   - `{notifyBaseUrl}/api/recharge/callback/aggregator`
   - 需要在聚合平台后台把「异步通知地址」填成上面这个。
4. 点「测试连通性」确认网关可达；保存后 `/api/recharge/pay-status` 的 `mode` 会变成 `aggregator`。
5. 第一次上线建议先下一个小额订单，确认回调能到账（订单状态变 `paid`、算力增加）。

密钥语义：输入框留空 = 保持原值；填 `__CLEAR__` = 清除；接口只回显 `keySet` / `appsecretSet` 布尔值，**任何接口都不返回明文密钥**（测试里对此有断言）。

### 5.3 环境变量（可选，优先级高于后台配置）

```
AGG_PROVIDER=epay
AGG_GATEWAY=https://pay.example.com
AGG_PID=1001
AGG_KEY=xxxxxx
AGG_NOTIFY_BASE_URL=https://ai.example.com
AGG_RETURN_BASE_URL=https://ai.example.com/#/recharge
```

### 5.4 安全约束

- 算力只在回调验签通过后入账，客户端不能自报金额/算力。
- 订单金额以服务端套餐表为准；回调金额（分）必须等于 `订单价 × 100`。
- 回调幂等：重复通知不会重复加算力；`tradeState` 非成功态不改订单。
- 回调里自报的 provider 一律不信，只用服务端配置的协议验签。
- 密钥存储沿用 `pay-config.json`（`AI_CANVAS_HOME` 下，0600），审计日志不落明文。

### 8.3 已知边界

1. **桌面端单机单令牌**：`server/security.js` 的机器令牌模型是「一台机器一枚令牌、一次代表一个用户」。同一个进程内切换账号 = 重新登录覆盖会话，这是设计而非缺陷；浏览器多用户要等云端化 P1（账号迁移到 PostgreSQL）。
2. **真实支付链路未跑**：本机没有易支付/虎皮椒的真实商户号，端到端用的是「签名自洽的回调」。上线前需要用自己的商户做一笔 0.01 元真实交易验证。
3. **自动查单候选口径**：目前只查 `pending` 且通道为空或 `aggregator` 的订单。若以后在发起支付时回写 `order.channel`，可以把条件收紧。
4. **退款是账面冲正**：真实资金退款仍需在支付平台后台操作，本后台负责算力与账目平齐。
